- **Symptom:** 15 open, invoiced rows have V and X blank: 6465-6477 GT190826A1 and 6478-6479 GT200826A1. They have a POD on 24-Aug. Y/Z, AA:AD and (before the fix in `2026-10-31-pod-status-blank-when-pick-date-blank.md`) AQ/AR are blank too.

- **Where:** data only. The Pick Pack folder 1Xi66o4A0I3GdtlNrh61XcEWNkT5UKmey has no `PickPackReport_20.08.2026`. The job (`read_pick_pack_files` → `build_pick_pack_lookup` → `_pick_pack_cells` in `scripts/gt_full_flow_fms_yes_no_all_or_latest.py`) keys V/X by Order No, so it has nothing to match.
- **Root cause:**
  - Each report is created the next morning for the previous day: PickPackReport_19.08.2026 at 20-Aug 03:59Z and 21.08.2026 at 22-Aug 03:58Z.
  - The report for 20-Aug, when these GTs were picked, was never exported.
  - Two files were created by hand on 20-Aug 10:46-10:48Z with odd names ("PickPackReport_05.08.2026" and "PickPackReport_28.08.2026_29.08.2026"). The job reads them (788 and 1,109 rows in the 23-Oct run), but they do not contain these orders.
  - Drive full-text search of the Pick Pack folder for O94111 / N89535 / N012216 / N89536 / GT190826A1 returns nothing. M892741 is found only in a POD PDF and in GT order templates.
- **Why it wasn't caught:**
  - The job reads every file in the folder whatever its name. It does not check for missing days.
  - The run-health check only warns when the NEWEST file is stale.
- **Fix:** no code change. The cause is a missing export, and the code already fills V/X for a blank cell as soon as the file exists.
  - Export Vinculum Pick Pack for 20-Aug-2026, all locations including N10, as `PickPackReport_20.08.2026` into the Pick Pack folder (nasher-miles-report-automation, date-range run).
  - The next "GT FMS Automation" run then fills V/X on the 15 rows (blank cells only, reason `refresh`).
  - With X filled, the status step computes Y/Z, AA:AD and the X-based AO.
  - Until then, AQ/AR on these rows come from the S-based fallback (commit "Status step: plan AO from S…").
